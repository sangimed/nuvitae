# Feature Specification: Import Existing Resume

**Feature Branch**: `main`

**Created**: 2026-07-28

**Status**: Ready for Planning

**Input**: User description: "Create Nuvitae's first product feature specification: importing an existing resume."

## Clarifications

### Session 2026-07-28

- Q: Which document formats, languages, text requirements, and upload limits are supported in the initial resume-import release? → A: PDF and DOCX only; French, English, and bilingual French-English; selectable text required; max 10 MB and 5 rendered pages.
- Q: How long should uploaded documents and unconfirmed import drafts be retained, and can users delete the source independently? → A: Source documents and all temporary or derived extraction artifacts are deleted no later than 7 days after original upload; confirmation does not restart or extend this period; users may delete the source earlier without deleting the confirmed structured resume.
- Q: How should extraction uncertainty be presented and resolved before structured resume creation? → A: Mark uncertain, missing, duplicate, and conflicting fields as “needs review”; user must confirm, edit, exclude, or intentionally leave each warning before creating the structured resume.
- Q: How should multiple roles within one employer and ongoing roles without an end date be represented? → A: Preserve each role as a separate work-experience role under the same employer; ongoing roles have no end date and display as “Present”.
- Q: What extraction strategy, progress, and timeout behaviour should the initial release use? → A: Deterministic extraction first; optional AI may classify sections or flag ambiguity after deterministic extraction; timeout after 3 minutes and show threshold-qualified partial extraction results plus retry/manual-entry options.
- Q: What are the initial configurable processing limits? → A: 10 MB file size, 5 rendered pages, 3 minutes foreground processing, 512 MiB parser-process memory, 1 active and 2 queued processing jobs per user, and 5 upload or processing-start attempts per rolling 10-minute window per authenticated user; production deployments may tune but not disable these limits.
- Q: What manual-entry fallback must exist for the empty application? → A: `/resumes/new/manual` creates a blank editable structured-resume draft without creating an imported document or import job and is reachable from initial creation plus all import failure states.

### Session 2026-07-30

- Q: How does the initial self-hosted release split AI and deterministic responsibilities? → A: Semantic parsing of supported PDF and DOCX resumes is AI-first. AI is responsible for semantic resume mapping and grouping of personal and contact information, headline, summary, work experiences, employers, roles, dates, locations, responsibilities, achievements, education, skills, languages, projects, certifications, and professional links. Deterministic processing remains responsible for file validation, supported format and language enforcement, file-size and page limits, unsafe/encrypted/malformed/unreadable document rejection, private storage, parser isolation and timeouts, output schema validation, evidence and provenance validation, no-invention checks, retention and deletion, warning generation, and explicit user review and confirmation. This supersedes the extraction-strategy clarification from 2026-07-28 and requires later amendment of FR-008, FR-020, FR-021, FR-023, SC-002, and SC-012 while preserving their IDs where possible.
- Q: What provider abstraction is required for AI-assisted import? → A: The import domain must depend only on a Nuvitae-owned provider abstraction and versioned Nuvitae extraction schema, never directly on Codex, OpenAI, ChatGPT, Claude, Ollama, provider-native JSON, or any provider SDK. The first adapter may target Codex authenticated through the user's existing ChatGPT subscription for self-hosted installations, but Codex is only the first adapter. The architecture must allow future adapters for local models, OpenAI-compatible endpoints, API-key providers, and a Nuvitae-managed hosted commercial provider. FR-019, FR-020, FR-021, and the Constitutional Requirements provider-independence wording require later amendment while preserving IDs where possible.
- Q: What authentication and credential scope applies to the first Codex integration? → A: The Codex integration is intended only for a user-controlled, self-hosted Nuvitae installation using that user's own ChatGPT subscription. The specification must not assume that a future hosted SaaS stores or reuses user ChatGPT subscription credentials. Credentials and session material must remain private, revocable, isolated from resume data, excluded from logs, inaccessible to other users, and separable from uploaded documents, import drafts, extracted content, and retained provenance. FR-005b, FR-026, FR-026a, and privacy-facing assumptions require later amendment while preserving IDs where possible.
- Q: What happens when no AI provider is connected or the configured provider cannot parse? → A: Nuvitae must not claim reliable full semantic parsing without an available AI provider. If no provider is connected, or the provider is unavailable, rate-limited, unauthenticated, disconnected, or out of subscription quota, the user must receive recoverable options to retry or reconnect the provider, choose another provider if configured, continue with limited deterministic partial extraction where available, or continue with manual entry. FR-007a, FR-020, FR-021, FR-025, FR-025f, FR-025g, SC-007, SC-012, and failure-state documentation require later amendment while preserving IDs where possible.
- Q: What evidence contract applies to AI-produced resume values? → A: Every AI-produced value remains an unconfirmed candidate until explicit user review and confirmation. Each candidate must include evidence linked to the uploaded document: source page or document location, exact source text or a source fragment identifier, whether the classification is explicit or inferred, and a confidence category. Unsupported AI-produced values must be rejected or marked unusable rather than silently accepted. FR-009, FR-009b, FR-010, FR-010b, FR-013, FR-013b, FR-015, FR-023, FR-023b, SC-006, and SC-011 require later amendment while preserving IDs where possible.
- Q: What output contract must provider adapters satisfy? → A: Provider adapters must translate provider responses into a versioned, strictly validated Nuvitae-owned structured response before the import domain sees them. Malformed output, unknown fields, invalid relationships, unsupported values, invented facts, and provider-native schema leakage must fail safely or become explicit review warnings. Provider-native JSON must not enter the import domain directly. FR-019, FR-021, FR-023, FR-026, and quality-gate wording require later amendment while preserving IDs where possible.
- Q: What privacy and prompt-injection safeguards apply to AI-first semantic parsing? → A: Uploaded documents remain untrusted input and may contain prompt injection. The configured AI provider receives only system-controlled extraction instructions and must not follow instructions embedded in the resume. User-facing disclosure must explain before provider use that resume content is sent to the configured AI provider. Full resume contents, prompts, credentials, provider session material, raw provider payloads, source snippets, and unnecessary personal data must be excluded from logs and user-visible diagnostics. FR-002, FR-006b, FR-022, FR-026, FR-026a, FR-027, SC-011, and SC-019 require later amendment while preserving IDs where possible.
- Q: What remains out of scope for this AI-first clarification? → A: Training a Nuvitae-owned model, selecting the hosted commercial provider, OCR, job-description adaptation, resume rewriting, ATS scoring, template selection, and final PDF generation remain out of scope. FR-028 remains directionally valid, but should later be amended to explicitly include training a Nuvitae-owned model, hosted commercial provider selection, and OCR while preserving the FR-028 ID where possible.
- Q: What is the corrected Codex product decision after the app-server spike? → A: The completed T189-T195 spike is a NO-GO only for the tested `codex app-server` 0.146.0 ChatGPT-managed authentication candidate. It does not reject Codex globally, direct OAuth, future Codex versions, or the AI-first architecture. Codex remains a candidate first self-hosted provider only through a separate direct-OAuth compatibility spike using a dedicated infrastructure-level credential broker and the existing provider-independent parser boundary. No production Codex implementation is authorized until that spike records a new explicit decision, and a new NO-GO remains acceptable.

### Session 2026-08-02

- Q: How is an optional resume field that is explicitly absent from the source represented? → A: The property is required and its value is JSON `null`; it is never omitted. This applies across PDF, DOCX, and plain-text imports and must be accepted by the strict schema and required by prompts and evaluation.
- Q: What is the scope of the absence rule? → A: All optional scalar and optional nested-object fields use required nullable properties; an absent optional section collection is `[]`, and an absent optional object is `null`, never `{}`. Thus `basics.phone`, `work_experiences[].location`, `work_experiences[].employment_type`, `education[].grade`, and `certifications[].issuer` are `null` when absent.
- Q: What evidence is required for absent fields? → A: A null field has no value evidence. It must be declared by path in a manifest `intentionally_absent_fields` declaration, may be supported by one absence diagnostic with `absence` provenance, and is evaluated as exact null plus no invented value; it is not an exact-recall fact.
- Q: What PDF evidence-coordinate model is canonical? → A: Preserve both deterministically: AI-result evidence uses canonical flattened `line`/`start`/`end` coordinates over the normalized extraction transcript, while the extraction provenance record carries page/item/offset coordinates and the adapter must provide a deterministic mapping between them. DOCX and plain text use their native provenance plus the same flattened transcript coordinates where supplied to the parser.
- Q: How are fact categories and T201 status governed? → A: Every expected fact and diagnostic must declare an explicit allowed provenance category. Category/path correctness is semantic evaluation, while enum membership and required presence are schema validation. `docs/research/codex-direct-semantic-parsing.md` is the canonical current-status source; historical task, checklist, and Campaign-B decision wording remains historical and must not override it. A dedicated reconciliation implementation task was required before any C04 authorization; C04 (and C05/C06) execution has since occurred under T243 with sanitized evidence, and the matrix is complete and all-passing.
- Q: What correction applies after the sanitized T201-C04 B01 result exposed physical-coordinate mismatches? → A: This supersedes the physical-source-location portion of the 2026-07-30 evidence-contract clarification. The LLM is responsible only for selecting grounded evidence using canonical flattened text coordinates (`line`, `start`, `end`) over the normalized extraction transcript. Physical PDF provenance (`page`, `item`, physical offsets) must be generated and verified deterministically by the PDF extraction/mapping layer after model output, not predicted by the LLM. Grounding validation first checks flattened bounds, fragment hashes, source grounding, no-invention, evidence validity, absent-field handling, ambiguity handling, and required fact recall against the flattened transcript; deterministic enrichment then maps valid flattened ranges to physical PDF provenance and fails only enrichment/provenance if that mapping cannot be produced. A semantic result MUST NOT fail solely because model-produced physical coordinates disagree with deterministic mapping, because model-produced physical coordinates are not part of the model contract. Plain text, DOCX, and PDF imports share one canonical evidence model: model/provider output cites flattened transcript evidence; import adapters retain native deterministic provenance and enrich validated evidence for review traceability. Historical evidence remains immutable. The sanitized C04 B01 result remains a failed live attempt under the contract active at execution time: schema passed, language passed, 23/23 real facts passed, 17/17 high-priority facts passed, absent-field and ambiguity handling passed, no-invention passed, and all 23 failures were `evidence_coordinate_mismatch` from the physical-coordinate layer. This clarification stops further T201-C04 live attempts, does not authorize C04 B02, and requires a follow-up implementation task to remove physical coordinates from model output requirements and shift PDF physical-provenance enrichment into deterministic post-processing.

## Community MVP Product Direction

The approved strategic direction replaces the earlier architecture-first and hardening-first strategy with a product-first MVP strategy. Nuvitae Community is the first MVP release. It is self-hosted, distributed through the existing Docker-first setup, free to use, and powered by the user's own Codex access connected through OAuth. It exists to prove the complete AI-powered resume experience before the hosted commercial edition is built.

**Community MVP product promise**: The Community MVP must allow a user to:

1. install and start Nuvitae through the documented Docker flow;
2. connect Codex through OAuth;
3. verify that the Codex connection is operational;
4. import a PDF or DOCX resume;
5. obtain an AI-backed structured draft;
6. review and correct imported information;
7. confirm the draft without silently losing unreviewed data;
8. edit the resume through a clean visual interface;
9. apply useful, reversible AI improvements;
10. render a credible resume template;
11. export an ATS-friendly PDF;
12. save and reopen the resume later.

**Codex OAuth is MVP-critical**: The direct Codex OAuth path must no longer be classified as paused, optional, post-validation, or merely experimental. The MVP must cover: start OAuth connection; browser authorization; callback handling; connection status; secure credential persistence; token refresh or reauthorization behavior; disconnect; provider-unavailable recovery; invocation through the validated Codex runtime path; semantic import; contextual AI editing; and privacy-safe errors and logs. Users must not be required to paste API keys for the primary Community journey. OAuth implementation details, tokens, app-server details, provider-runtime vocabulary, and model internals must not be exposed in the normal UI; the normal UX uses plain actions such as "Connect Codex", "Reconnect Codex", "Codex is ready", "Codex connection expired", and "Disconnect".

**UI/UX standard**: The Community MVP must not look like a developer prototype. It requires a coherent application shell, modern typography and spacing, clear navigation, a clean Codex connection flow, a polished upload flow, a simplified review experience, a usable visual editor, persistent or easily accessible live preview, contextual AI actions, designed loading/empty/success/error states, close visual fidelity between preview and exported PDF, and responsive behavior for desktop and mobile. Technical installation may target self-hosters, but normal resume creation must not feel technical.

**Retained safety baseline**: authentication where required by the current deployment model; ownership isolation; private storage; privacy-safe logging; secure server-side credential handling; essential upload validation; cost and rate limiting where applicable; no cross-user access; no unsafe document execution; and recoverable user-facing failures. Advanced hardening, rare edge cases, exhaustive retention, provider breadth, horizontal scale, and hosted billing may be deferred (see Deferred Capabilities).

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Start From an Existing Resume (Priority: P1)

A non-technical user who chooses to create a resume is prominently offered the option to import an existing resume, can upload a supported document, and receives clear progress updates while Nuvitae validates and extracts information.

**Why this priority**: Import-first onboarding is the core value of the first-session experience; users should not have to recreate a resume manually before seeing value.

**Independent Test**: Can be tested by starting resume creation, selecting import, uploading a supported resume document, and verifying that the user sees understandable validation, processing progress, and a draft extraction result without seeing technical internals.

**Acceptance Scenarios**:

1. **Given** a user starts creating a resume, **When** the creation flow opens, **Then** importing an existing resume is presented as the primary recommended path while manual entry remains available.
2. **Given** a visitor is not authenticated, **When** they try to upload a resume, **Then** Nuvitae requires sign-in before accepting a file.
3. **Given** a user selects import, **When** the upload step appears, **Then** the user sees that the initial release accepts PDF and DOCX resumes in French, English, or bilingual French-English up to 10 MB and 5 rendered pages, plus privacy guidance and a clear way to choose a file.
4. **Given** a user uploads a supported resume document, **When** validation and extraction are in progress, **Then** the user sees plain-language progress states such as checking document, reading content, organizing resume sections, and preparing review.
5. **Given** the provider-independent AI parser returns at least one supported resume candidate with required document evidence, **When** extraction completes, **Then** the user is taken to a review interface containing the extracted resume information.
6. **Given** extraction has not completed within 3 minutes, **When** the processing limit is reached, **Then** the user sees a timeout state with any partial extraction results that meet the draft creation threshold, retry, replacement upload, and manual-entry options.
7. **Given** the user chooses manual entry from initial resume creation, **When** the action is activated, **Then** Nuvitae opens `/resumes/new/manual` and creates a blank editable structured-resume draft without creating an imported document or import job.

### User Story 2 - Review and Correct Extracted Information (Priority: P1)

A user reviews the extracted personal information, headline, summary, work experience, education, skills, languages, projects, certifications, and professional links in a simple visual interface where uncertain or incomplete fields are clearly marked.

**Why this priority**: Extracted content is untrusted and unverified until the user confirms it; the feature only creates value if users can detect and correct mistakes easily.

**Independent Test**: Can be tested by importing a resume with complete, missing, and ambiguous information and verifying that every extracted field can be corrected, removed, completed, or left out before confirmation.

**Acceptance Scenarios**:

1. **Given** extraction produced structured resume candidates from at least one supported field with required document evidence, **When** the review screen opens, **Then** information is grouped into recognizable resume sections rather than raw data structures.
2. **Given** a field was missing, ambiguous, duplicated, unusually formatted, or extracted with low confidence, **When** the user reviews the relevant section, **Then** the issue is visually identified as needing review with plain-language guidance and a clear action to confirm, edit, exclude, or intentionally leave it.
3. **Given** any extracted field is visible in review, **When** the user edits, removes, or completes that field, **Then** the review state updates without changing the uploaded source document.
4. **Given** a section contains no supported fields with required document evidence, **When** review is shown, **Then** the user can leave the section empty, add information manually, or remove the section from the imported resume draft.
5. **Given** the imported resume contains multiple roles at the same employer, **When** review is shown, **Then** each role is preserved as a separate work-experience role grouped under that employer.
6. **Given** extracted information is semantically grouped, ambiguously classified, or associated with a work experience by inference, **When** review is shown, **Then** that inference is marked as needing confirmation before structured resume creation.

### User Story 3 - Confirm Creation of Structured Resume (Priority: P1)

A user explicitly confirms the reviewed extraction before Nuvitae creates structured resume data, and can understand that the original uploaded document remains distinct from the structured resume.

**Why this priority**: The master resume must not be silently created from unverified extraction, and the source document must remain a separate artifact.

**Independent Test**: Can be tested by completing import review, confirming creation, and verifying that structured resume data is created only after confirmation and that the uploaded document is still represented as an import source rather than an editable resume.

**Acceptance Scenarios**:

1. **Given** the review contains warnings that have not been addressed, **When** the user attempts to create the resume, **Then** Nuvitae blocks confirmation, explains what still needs review, and allows the user to confirm, edit, exclude, or intentionally leave each warning.
2. **Given** the user confirms the reviewed information, **When** creation succeeds, **Then** Nuvitae creates structured resume data from the confirmed fields and marks those fields as user-confirmed.
3. **Given** the structured resume has been created, **When** the user views resume content, **Then** edits affect the structured resume data and not the uploaded source document.
4. **Given** the user leaves the import flow before confirmation, **When** they return within 7 days of upload, **Then** they can resume review or discard the import draft.
5. **Given** the user confirms the structured resume, **When** the original upload reaches 7 days old, **Then** the uploaded source document and all source-reconstructing extraction artifacts are deleted while the confirmed structured resume remains available until the user deletes it.

### User Story 4 - Recover From Partial Extraction or Failure (Priority: P2)

A user receives understandable next steps when a document cannot be fully imported, including partial results, retry, replacement upload, manual entry, and deletion options.

**Why this priority**: A threshold-qualified partial extraction is better than a complete failure, and recovery paths preserve user trust when parsing is imperfect.

**Independent Test**: Can be tested with unreadable, unsupported, password-protected, image-heavy, oversized, duplicate, and partially readable documents and verifying that each case gives a clear outcome and recovery path.

**Acceptance Scenarios**:

1. **Given** at least one supported resume candidate can be extracted with required document evidence but one or more expected sections are missing or unprocessed, **When** processing completes, **Then** Nuvitae shows a partial extraction for review and identifies missing or unprocessed sections.
2. **Given** the uploaded document is unsupported or cannot be safely processed, **When** validation fails, **Then** the user sees a non-technical explanation and can upload a different file or continue manually.
3. **Given** processing fails after upload, **When** the failure state appears, **Then** the user can retry, replace the document, delete the uploaded document, or continue with manual entry.
4. **Given** no AI provider is connected or the configured provider is unavailable, rate-limited, unauthenticated, disconnected, or out of subscription quota, **When** the user reaches the recovery state, **Then** Nuvitae explains that reliable full semantic parsing is unavailable and offers retry or reconnect, another configured provider if available, limited deterministic partial extraction where available, and manual entry.
5. **Given** deterministic validation completes without failure and an AI provider is connected, **When** semantic extraction starts, **Then** the provider-independent AI parser is used as the primary semantic mapping and grouping path while deterministic processing remains responsible for validation, safety, isolation, storage, schema validation, evidence validation, provenance, no-invention checks, review, confirmation, and retention.
6. **Given** the user closes the page or temporarily loses connectivity after upload, **When** they return before the 7-day expiry, **Then** the accepted upload, processing state, and saved review draft can be resumed by that same user.
7. **Given** the user explicitly cancels an import, **When** cancellation is confirmed, **Then** processing stops and the source document plus all temporary or derived extraction artifacts are scheduled for deletion.
8. **Given** the user returns to an expired import draft, **When** the draft is opened, **Then** Nuvitae shows an explicit expiry message and offers re-upload or manual entry.
9. **Given** no supported candidate can be associated with required document evidence, **When** extraction completes, **Then** no review draft is created and Nuvitae offers another upload or manual entry.
10. **Given** a document contains a resume plus unrelated pages, **When** resume content can be clearly separated, **Then** only the identified resume content is proposed and excluded content is disclosed.
11. **Given** a document contains mixed resume and unrelated content that cannot be clearly separated, **When** validation or extraction detects the ambiguity, **Then** Nuvitae asks the user to upload a resume-only document or continue manually.
12. **Given** a document is outside French, English, or bilingual French-English, **When** validation or extraction detects the unsupported language, **Then** no import review draft is created and Nuvitae offers another upload or `/resumes/new/manual`.
13. **Given** an unsupported-language document contains explicitly detectable contact information, **When** Nuvitae can safely detect those contact fields, **Then** it may show a temporary contact-only preview with an unsupported-language warning and requires explicit user confirmation before transferring those fields to `/resumes/new/manual`.
14. **Given** parser memory exceeds the configured 512 MiB limit, **When** the isolated parser process is terminated, **Then** no review draft is created from abruptly terminated partial output and the user receives retry, replacement-upload, and manual-entry options.

### User Story 5 - Complete Import Accessibly (Priority: P1)

A user can complete upload, processing, review, confirmation, retry, and deletion flows with accessible labels, screen-reader status updates, keyboard-only navigation, and recoverable focus behaviour.

**Why this priority**: Accessibility and recovery are constitutional release gates for core flows, and import is a primary onboarding path.

**Independent Test**: Can be tested by completing upload, validation failure, processing, warning review, confirmation, retry, cancellation, and source deletion with keyboard-only navigation and assistive technology checks.

**Acceptance Scenarios**:

1. **Given** any upload, review, retry, confirmation, cancellation, or deletion control is shown, **When** inspected with assistive technology, **Then** it has an accessible name and label that identifies its purpose.
2. **Given** processing starts, succeeds, times out, is cancelled, or fails, **When** the state changes, **Then** the state is announced to screen-reader users without exposing technical internals.
3. **Given** a field or section warning is displayed, **When** colour is unavailable or not perceived, **Then** the warning remains identifiable through text and non-colour visual treatment.
4. **Given** upload validation fails, **When** the error is shown, **Then** focus moves to an error summary that explains the problem and available recovery actions.
5. **Given** the user closes a confirmation, cancellation, retry, or deletion dialog, **When** the dialog closes, **Then** focus returns to the control or next logical step that preserves task context.
6. **Given** the user uses only a keyboard, **When** they complete import review, explicit confirmation, retry, cancellation, or source deletion, **Then** all required actions are reachable, operable, and visibly focused.

### User Story 6 - Protect Imported Resume Data (Priority: P1)

A user's imported resume, extracted content, processing state, and review draft remain private to that user and are removed according to explicit retention and deletion rules.

**Why this priority**: Resume imports contain sensitive personal data, so authorization, isolation, resource limits, and deletion are release-blocking product behaviours.

**Independent Test**: Can be tested by attempting cross-user access, exceeding upload and processing limits, importing hostile documents, deleting source documents, and checking that only allowed structured resume provenance remains.

**Acceptance Scenarios**:

1. **Given** User A initiates an import, **When** User B attempts to access, resume, confirm, or delete User A's source document, processing state, temporary artifacts, or draft, **Then** access is denied without exposing personal data.
2. **Given** a user exceeds upload or processing attempt limits, **When** they attempt another upload or extraction, **Then** Nuvitae rejects the operation with an appropriate rate-limit response such as HTTP 429, includes a Retry-After value where applicable, and shows a plain-language recovery message.
3. **Given** a document contains macros, scripts, active objects, links, hidden instructions, or prompt-injection text, **When** validation and extraction run, **Then** that content is not executed or treated as application or AI instructions.
4. **Given** a malformed or hostile document is processed, **When** validation or extraction fails, **Then** no other user's documents, processing state, import draft, or temporary artifacts are exposed or affected.
5. **Given** the user deletes the source document before automatic expiry, **When** deletion completes, **Then** extracted raw text, field source snippets, page references, thumbnails, temporary files, cached parsing results, future OCR outputs, embeddings if any, and equivalent source-reconstructing artifacts are deleted.
6. **Given** the source document has been deleted and a structured resume remains, **When** the user views the structured resume, **Then** it contains no raw source snippets and may show only minimal non-sensitive provenance such as “imported from initial resume” and “confirmed by user”.

### User Story 7 - Connect Codex Through OAuth (Priority: P1)

A Community user connects their own Codex access to Nuvitae through a browser OAuth flow from the normal UI, verifies that the connection works, and manages it (reconnect, disconnect) with plain-language status and recovery actions.

**Why this priority**: Codex OAuth is the primary AI connection path for the Community MVP and part of onboarding; semantic import and AI editing both depend on it.

**Independent Test**: Start the connection from onboarding, complete browser authorization, verify "Codex is ready" status, expire/disconnect/reconnect, and confirm no token or provider detail appears in the UI.

**Acceptance Scenarios**:

1. **Given** a user completes installation and onboarding, **When** they reach the connection step, **Then** Nuvitae offers a single clear "Connect Codex" action that starts the browser OAuth flow without requiring an API key.
2. **Given** the user authorizes Nuvitae in the browser, **When** the OAuth callback completes, **Then** Nuvitae shows "Codex is ready" and connection status updates without exposing tokens, model names, or provider-runtime details.
3. **Given** the user has an active Codex connection, **When** they attempt an import, **Then** semantic parsing runs through the validated Codex path behind the provider-independent boundary.
4. **Given** the Codex connection expires, is revoked, or becomes unavailable, **When** the user needs AI parsing or editing, **Then** Nuvitae shows a plain-language state such as "Codex connection expired" and offers reconnect and provider-unavailable recovery, without losing uploaded resumes, drafts, or structured resumes.
5. **Given** the user disconnects Codex, **When** they confirm the disconnect, **Then** local credentials are revoked/deleted by the credential-owning broker, connection status shows disconnected, and resumes, drafts, and structured resumes remain intact.
6. **Given** a user connects, disconnects, or reconnects, **When** any OAuth or token event occurs, **Then** no authorization code, access token, refresh token, account identifier, authorization URL, or provider-runtime detail is exposed to the web application, browser storage, API responses, domain objects, worker job payloads, logs, or diagnostics.

### User Story 8 - Edit, Preview, and Export the Resume (Priority: P1)

After confirmation, a user edits the resume in a clean visual editor, sees a live preview rendered from a credible template, and exports an ATS-friendly PDF. Resumes can be saved and reopened later from a minimal dashboard.

2. **Given** the user edits content or reorders a section, **When** changes are saved, **Then** the live preview updates to reflect the current template and a clear "Saving… / Saved / Error — retry" status is shown.

5. **Given** the user leaves the application and returns, **When** they open the dashboard, **Then** saved resumes are listed and can be reopened for continued editing.

### User Story 9 - Improve With Reversible AI Actions (Priority: P1)

Up to five contextual AI actions improve the resume through the user's own Codex connection. Every change is previewed before replacement, explicitly accepted or rejected, regenerable, and undoable, and no action may invent facts.

**Why this priority**: Reversible, fact-preserving AI improvement is the core value demonstration of the Community MVP without risky silent AI writes.

**Independent Test**: Invoke each available AI action on a field or section, review the before/after change, accept, reject, regenerate, and undo, and verify no invented facts reach the resume.

**Acceptance Scenarios**:

1. **Given** an editable field or section, **When** the user invokes an AI action, **Then** Nuvitae shows the original and proposed content side by side and applies nothing without an explicit accept.
2. **Given** a proposal is shown, **When** the user accepts, rejects, or regenerates it, **Then** the resume updates only on accept, the change can be undone, and the rejected/regenerated proposal does not modify content.
3. **Given** an AI action produces a change, **When** the user undoes it, **Then** the resume returns to the last saved state without data loss.
4. **Given** the AI edits any field, **When** the change is generated or reviewed, **Then** it introduces no new names, dates, companies, metrics, or other facts not present in the source or user-entered text.
5. **Given** the Codex connection is unavailable, expired, or revoked, **When** the user invokes an AI action, **Then** Nuvitae explains in plain language and offers reconnect or retry without pretending the action succeeded.
6. **Given** the AI action surface is displayed, **When** any proposal or failure is shown, **Then** no prompts, model identifiers, tokens, provider-runtime state, queues, workers, or internal schemas are exposed.

### Edge Cases

- The uploaded file is not one of the supported resume document formats.
- The file is empty, corrupted, unreadable, password-protected, encrypted, or contains no extractable text.
- The file is image-only, scanned, or otherwise lacks selectable text.
- The file is larger than 10 MB, has more than 5 rendered pages, or extraction reaches the 3-minute processing timeout.
- The isolated parser process exceeds 512 MiB memory and is terminated before draft creation.
- The DOCX rendered page count exceeds the 5-page limit.
- The document is in an unsupported language, or language detection cannot identify French, English, or bilingual French-English content.
- The document contains multiple resumes, cover letters, references, portfolios, or unrelated pages.
- The same information appears in several places with conflicting values, such as different phone numbers, employers, or dates.
- Dates are partial, ambiguous, inconsistent, future-dated, or expressed in different regional formats.
- The same employer contains multiple roles, promotions, overlapping role dates, or an ongoing role without an end date.
- Contact details, links, certifications, skills, or languages are embedded in headers, footers, tables, columns, icons, or unusual layouts.
- The document contains malicious content, hidden text, prompt-injection instructions, macros, scripts, active objects, links to unsafe locations, or misleading instructions aimed at the extraction process.
- The user cancels upload, closes the page during processing, loses connectivity, or returns more than 7 days after upload.
- A user wants to delete the uploaded document before confirming structured resume creation.
- Another user attempts to access, resume, confirm, or delete the import.
- Upload or processing attempts exceed product rate limits or concurrent work limits.
- Extraction cannot associate any supported candidate with required document evidence, but the user still wants to create a resume manually.
- No AI provider is connected, or the configured provider is unavailable, rate-limited, unauthenticated, disconnected, or out of subscription quota.
- A user chooses manual entry from initial creation, unsupported-file, no-usable-extraction, timeout, processing-failure, expired-draft, unsupported-language, no-provider, provider-unavailable, provider-rate-limited, provider-unauthenticated, or provider-quota-exceeded states.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: Nuvitae MUST present importing an existing resume as the primary recommended path when a user chooses to create a resume, while keeping manual creation available. The import option MUST be the first and most prominent create-resume action in the standard onboarding flow, and manual entry MUST remain visible as a secondary action rather than hidden behind error states or technical settings.
- **FR-002**: Nuvitae MUST explain supported document formats, languages, upload limits, expected processing behavior, AI provider use, and privacy handling before upload in language understandable to non-technical users, including that resume content is sent to the configured AI provider when provider-backed semantic parsing is used.
- **FR-003**: Nuvitae MUST accept only PDF and DOCX resume documents in French, English, or bilingual French-English for the initial release.
- **FR-003a**: Nuvitae MUST enforce a maximum file size of 10 MB and a maximum rendered document length of 5 pages for both PDF and DOCX uploads.
- **FR-003b**: Nuvitae MUST explain that semantic extraction is unsupported for other languages and offer another upload or `/resumes/new/manual`.
- **FR-003c**: Nuvitae MUST NOT create an import review draft for documents outside French, English, or bilingual French-English. Explicitly detectable contact information MAY be displayed in a temporary contact-only preview with a clear unsupported-language warning, limited to name, email address, phone number, location, and professional links detected by deterministic patterns. The user MUST explicitly confirm before those contact fields are transferred into the manual-entry flow, transferred fields MUST be marked as user-added, and contact-only detection in an unsupported-language document MUST NOT satisfy the import-draft creation threshold.
- **FR-004**: Nuvitae MUST reject unsupported, empty, unsafe, unreadable, password-protected, oversized, over-page-limit, or corrupted files with plain-language reasons and recovery actions.
- **FR-005**: Nuvitae MUST treat every uploaded document and all extracted content as untrusted input until validated and confirmed by the user.
- **FR-005a**: Nuvitae MUST require authentication before accepting a resume upload.
- **FR-005b**: Nuvitae MUST allow only the user who initiated an import to access, resume, confirm, or delete its source document, processing state, temporary artifacts, provider session material, and import draft.
- **FR-005c**: Nuvitae MUST limit each authenticated user to 5 upload or processing-start attempts per rolling 10-minute window.
- **FR-005d**: When upload, processing-start, active-job, or queued-job limits are reached, Nuvitae MUST reject the operation, use an appropriate rate-limit response such as HTTP 429, include a Retry-After value where applicable, and show a plain-language recovery message.
- **FR-005e**: Re-uploading the same file or repeatedly uploading materially identical source content MUST create a separate import attempt owned by the same user, count against the same rolling upload and processing-start limits, and receive its own retention deadline based on that attempt's original upload time. Nuvitae MAY identify repeated uploads for user guidance, but MUST NOT merge drafts, reuse source-reconstructing artifacts across imports, or extend a previous import's retention deadline because of a duplicate upload.
- **FR-006**: Nuvitae MUST validate uploaded documents before semantic extraction and prevent unsafe document content from executing or influencing product behavior outside the import task.
- **FR-006a**: Nuvitae MUST require selectable text for import. Fully scanned, image-only, or fully non-selectable documents MUST be rejected with recovery actions. Mixed image/text or partially selectable PDF/DOCX documents MAY be processed only from selectable text when at least one supported field can be explicitly sourced from that text; non-selectable regions MUST NOT be treated as extracted content and MUST be disclosed as unprocessed or missing where relevant.
- **FR-006b**: Nuvitae MUST never execute or treat embedded macros, scripts, active objects, links, hidden instructions, or document text as application instructions or AI instructions.
- **FR-006c**: Nuvitae MUST enforce initial configurable processing limits of 10 MB maximum uploaded file size, 5 rendered pages maximum, 3 minutes maximum foreground processing duration, 512 MiB maximum parser-process memory, and per-user concurrency of 1 active processing job plus 2 queued jobs.
- **FR-006d**: Nuvitae MUST isolate document processing so a malformed or hostile document cannot expose or affect another user's documents, processing state, import draft, or temporary artifacts.
- **FR-006e**: Nuvitae MUST keep processing and rate limits configurable but MUST NOT allow production deployments to disable them.
- **FR-006f**: Nuvitae MUST hard-enforce parser memory in an isolated process, terminate the parser process on memory excess, prevent review-draft creation from abruptly terminated partial output, clean up source files and source-reconstructing artifacts for the failed attempt, and offer retry, replacement-upload, and manual-entry options.
- **FR-007**: Nuvitae MUST show understandable progress states for validation, extraction, review preparation, success, timeout, cancellation, retry, and failure.
- **FR-007a**: Nuvitae MUST stop foreground extraction after 3 minutes and show any partial extraction results that meet the draft creation threshold with retry, replacement upload, provider reconnect or provider selection where applicable, and manual-entry options.
- **FR-008**: When an AI provider is connected, Nuvitae MUST use a provider-independent AI parser as the primary semantic extraction path for mapping and grouping available resume information into structured draft fields for personal and contact information, professional headline, summary, work experiences, employers, roles, dates, locations, responsibilities, achievements, education, skills, languages, projects, certifications, and professional links.
- **FR-008a**: Nuvitae MUST preserve multiple roles within the same employer as separate work-experience roles grouped under that employer when the relationship is explicit in the document evidence; inferred grouping MUST be marked as needing review.
- **FR-008b**: Nuvitae MUST represent ongoing roles with no end date in structured data and display them as “Present” in the review flow.
- **FR-009**: Nuvitae MUST preserve source traceability during review by indicating whether each candidate field came from explicit document content, was inferred, was added by the user, or was changed by the user during review.
- **FR-009a**: Nuvitae MUST NOT retain raw source snippets, page references, thumbnails, extracted raw text, cached parsing results, future OCR outputs, embeddings, or other source-reconstructing artifacts after source document deletion.
- **FR-009b**: While source-reconstructing artifacts still exist, source locations MUST be specific enough for review traceability: PDF locations include page number plus text-item or bounding-box reference, and DOCX locations include Office Open XML package part plus paragraph, table/cell where applicable, run, and character-offset reference. DOCX review copy MUST NOT promise rendered coordinates unless they are actually produced by the adapter.
- **FR-009c**: Every AI-produced resume candidate MUST include evidence linked to the uploaded document using the provider-facing canonical flattened evidence coordinates (`line`, `start`, `end`) over the normalized extraction transcript, plus exact source text or a source fragment identifier, explicit-versus-inferred classification, and confidence category. AI/provider output MUST NOT be required or trusted to produce physical PDF coordinates such as page number, text-item ordinal, bounding box, or physical offsets.
- **FR-009d**: For every optional resume scalar or optional nested-object field that is explicitly absent from the source, the versioned Nuvitae extraction response MUST include the property with JSON `null`; it MUST NOT omit the property or infer a value. This rule applies identically to PDF, DOCX, and plain-text imports. `basics.phone`, `work_experiences[].location`, `work_experiences[].employment_type`, `education[].grade`, and `certifications[].issuer` are required nullable properties. An absent optional section collection is an empty array, and an absent optional object is `null`, never an empty object.
- **FR-009e**: A null absent field MUST carry no value evidence and MUST NOT count as an exact-recall fact. Fixture or evaluation manifests MUST declare each expected absent path in `intentionally_absent_fields`; an optional bounded absence diagnostic may cite the source using the `absence` category. Validation MUST reject omission where null is required and reject any non-null value at a declared absent path, so diagnostics distinguish schema omission from an invented value without lowering grounding, recall, or no-invention thresholds.
- **FR-009f**: Provider-facing semantic evidence MUST use flattened `line`, `start`, and `end` coordinates over a versioned normalized extraction transcript, with fragment hashes and bounds validated against that transcript. For PDF, the adapter MUST order pages ascending and then source text items by the extractor's stable reading-order ordinal, emit one transcript line per source text item, and deterministically enrich validated flattened ranges with source page, item ordinal, and zero-based item offsets after model output; its mapping is therefore `line`→(page,item) and `start`/`end`→the same item offsets after the transcript's declared normalization. The mapping definition and offset unit MUST be versioned, emitted with the provenance record, and tested with multi-page, multi-item, whitespace, and multi-column input; it cannot be inferred from a one-page fixture. DOCX and plain-text provenance MUST likewise retain their native source locations while using the same flattened transcript coordinates whenever text is sent to a provider.
- **FR-009g**: Every expected fact and diagnostic in a current v2 import fixture or provider response contract MUST declare exactly one provenance category. The only permitted v2 categories are `basics`, `work`, `education`, `skills`, `languages`, `certifications`, `ambiguity`, and `absence`. Semantic category-to-path rules are: `basics` for basics fields; `work` for work experience fields and work highlights; `education` for education fields; `skills` for skills fields; `languages` for languages fields; `certifications` for certifications fields; `ambiguity` for ambiguity diagnostics; and `absence` for optional absence diagnostics or declarations where applicable. Schema validation MUST require a permitted category; semantic evaluation MUST verify category/path correctness and fail closed for a missing, unrelated, or mismatched category. Immutable v1 C01-C03 historical outputs may retain their recorded legacy compatibility vocabulary (`identity`, `summary`, `skill`, `language`, `certification`, and `warning`), but that vocabulary is historical only and is not normative for new v2 manifests.
- **FR-009h**: Semantic grounding evaluation MUST validate model output before deterministic provenance enrichment by checking schema validity, required nullable absent fields, ambiguity diagnostics, flattened coordinate bounds, fragment hashes, source grounding, evidence-category/path correctness, fact recall, high-priority fact recall, and no-invention against the normalized transcript. After that semantic grounding pass, the document extraction/mapping layer MUST enrich valid flattened evidence with deterministic native provenance for review traceability: PDF page/item/physical offsets, DOCX package part/paragraph/table/cell/run/character offsets where available, and plain-text native line/offset metadata. A semantic result MUST NOT fail solely because model-produced physical coordinates disagree with deterministic mapping; model-produced physical coordinates are invalid input to the semantic contract rather than semantic evidence.
- **FR-009i**: Plain text, DOCX, and PDF imports MUST share the same canonical evidence contract for semantic parsing: the provider receives a normalized transcript and may cite only flattened `line`, `start`, and `end` ranges over that transcript, while each import adapter owns deterministic native provenance extraction, mapping, and enrichment after model output.
- **FR-010**: Nuvitae MUST identify missing, ambiguous, conflicting, duplicate, and low-confidence information in the review interface using plain-language labels and visual emphasis.
- **FR-010a**: Nuvitae MUST mark uncertain, missing, duplicate, and conflicting fields as needing review until the user confirms, edits, excludes, or intentionally leaves each warning.
- **FR-010b**: Field confidence status MUST use explicit categories of `high`, `medium`, `low`, and `not_applicable`. Low confidence applies when extraction can associate a value with document evidence but cannot reliably classify the section, field path, date meaning, role association, semantic grouping, or duplicate/conflict resolution without user review. User-added fields use `not_applicable` unless later compared with source content.
- **FR-011**: Nuvitae MUST allow the user to edit, remove, complete, or exclude every extracted field before creating the structured resume.
- **FR-012**: Nuvitae MUST allow users to leave optional sections empty when the uploaded resume does not contain relevant information.
- **FR-013**: Nuvitae MUST create a review draft only when at least one supported resume candidate is extracted from document content and associated with required evidence.
- **FR-013a**: Nuvitae MUST define partial extraction as at least one supported candidate with required document evidence plus one or more expected sections that are missing or cannot be processed.
- **FR-013b**: Nuvitae MUST NOT create a review draft from inferred-only information.
- **FR-013c**: Nuvitae MUST follow the no-supported-field failure path when extraction cannot associate any supported candidate with required document evidence.
- **FR-014**: Nuvitae MUST create the structured resume only after the user explicitly confirms the reviewed extraction.
- **FR-015**: Nuvitae MUST mark extracted information as unverified until explicit user confirmation.
- **FR-016**: Nuvitae MUST keep the uploaded source document distinct from the structured resume data and MUST NOT directly modify the source document.
- **FR-017**: Nuvitae MUST delete the uploaded source document and all temporary or derived extraction artifacts no later than 7 days after the original upload.
- **FR-017a**: Nuvitae MUST NOT restart or extend source document or extraction artifact retention when the user confirms the structured resume.
- **FR-017b**: Nuvitae MUST retain the confirmed structured resume until the user deletes it, independent of source document expiry or deletion.
- **FR-017c**: Deletion verification MUST record whether the source document, extracted raw text, field source snippets, page references, thumbnails, temporary files, cached parser outputs, future OCR outputs, embeddings if any, and equivalent source-reconstructing artifacts were removed or were already absent before the 7-day retention deadline.
- **FR-018**: Nuvitae MUST provide a way to delete the uploaded source document before automatic expiry.
- **FR-018a**: Deleting the uploaded source document MUST also delete extracted raw text, field source snippets, page references, thumbnails, temporary files, cached parsing results, future OCR outputs, embeddings if any, and any other derived artifact capable of reconstructing source content.
- **FR-018b**: After source deletion, the structured resume MAY retain only minimal non-sensitive provenance such as “imported from initial resume” and “confirmed by user”.
- **FR-018c**: Nuvitae MUST allow source document deletion after a structured resume has been created without deleting the confirmed structured resume unless the user separately chooses to delete it.
- **FR-018d**: If the user deletes the source document before structured resume confirmation, Nuvitae MUST remove source-reconstructing artifacts and MUST NOT show raw snippets, page references, thumbnails, extracted raw text, or source-location previews afterward. The remaining review state MAY show user-entered corrections, field values already saved in the draft, warning statuses, and minimal non-sensitive provenance, but confirmation MUST be blocked unless at least one supported field is user-confirmed and every warning remains addressable without source artifacts; otherwise Nuvitae MUST offer discard and manual-entry recovery.
- **FR-018e**: Source deletion, cancellation, discard, expiry, and retention jobs MUST be idempotent. If processing is already in progress, cancellation or deletion MUST stop future processing where possible, prevent new source-reconstructing artifacts from being committed after the deletion decision, and schedule cleanup for artifacts that already exist. If the source is already deleted or a retention job is already scheduled, repeated delete, cancel, discard, or expiry actions MUST return the current deletion state without recreating artifacts or extending retention.
- **FR-018f**: Deleting source artifacts MUST NOT delete a confirmed structured resume, and confirming a structured resume MUST NOT cancel an already scheduled source/artifact deletion job or extend the deletion deadline.
- **FR-019**: Nuvitae MUST avoid showing raw JSON, YAML, prompts, parsing internals, model names, provider credentials, provider session details, or provider configuration in the end-user import flow, except for plain-language disclosure that resume content is sent to the configured AI provider when provider-backed semantic parsing is used.
- **FR-020**: Nuvitae MUST keep deterministic processing responsible for document validation, supported format and language enforcement, file-size and page limits, unsafe/encrypted/malformed/unreadable document rejection, private storage, parser isolation and timeouts, schema validation, evidence and provenance validation, no-invention enforcement, warning generation, review, confirmation, retention, and deletion; deterministic processing MUST NOT be specified as the primary semantic resume reconstruction path.

Codex MUST remain an adapter rather than a permanent dependency of the import domain. The configured AI provider MUST receive system-controlled extraction instructions and MUST NOT follow instructions embedded in the resume.

### Key Entities _(include if feature involves data)_

- **Imported Document**: The uploaded source file supplied by the user. It has an initiating user, visible filename, upload status, validation status, deletion status, and retention expiry based on the original upload time. It remains distinct from the structured resume, is never directly modified, and is deleted no later than 7 days after original upload unless the user deletes it earlier.
- **Derived Extraction Artifact**: Any temporary or derived data capable of reconstructing source content, including extracted raw text, field source snippets, page references, thumbnails, temporary files, cached parsing results, future OCR outputs, embeddings if any, and equivalent artifacts. It has the same owner and retention deadline as the imported document.
- **Temporary Contact Preview**: A short-lived unsupported-language recovery view containing only explicitly detected contact fields and an unsupported-language warning. It is not an import draft, does not satisfy the draft creation threshold, requires explicit user confirmation before transfer to manual entry, and follows the same deletion and logging restrictions as derived extraction artifacts.
- **Import Draft**: A temporary reviewable workspace containing extracted resume fields, warnings, source references while the source exists, and user corrections before structured resume creation. It belongs to the initiating user, may be resumed only before the 7-day expiry, and is retained for up to 7 days after original upload unless the user deletes it earlier.
- **Extracted Field**: An unconfirmed candidate resume value found during import, such as a phone number, role title, employer, education item, skill, language, project, certification, or link. It has a section, value, source status, required evidence while the source exists, explicit-versus-inferred classification, confidence status, review status, and optional warning.
- **AI Provider Adapter**: A provider-specific integration behind the Nuvitae-owned import provider abstraction. For the Community MVP, Codex direct OAuth is the production primary adapter, still pending the direct-OAuth decision-gate conditions; future adapters may target local models, OpenAI-compatible endpoints, API-key providers, or a hosted commercial provider selected outside this feature.
- **AI Provider Runtime Connection**: The user's connection to a configured AI provider for semantic parsing. It has provider identity, connection state, capability state, authentication status, disconnection state, and user-visible availability status, and it exposes no raw provider credentials or tokens to the resume-import domain, web application, normal worker orchestration, provider-independent contracts, or ordinary API responses.
- **Codex Credential Broker**: A dedicated infrastructure-level boundary that may own encrypted Codex access and refresh tokens when the provider integration requires them. It exposes only provider-neutral connection status and semantic invocation operations to the rest of Nuvitae, and it supports user-controlled connect, reconnect, disconnect, local revocation, and deletion of locally stored provider credentials.
- **Nuvitae Extraction Response**: The versioned, strictly validated structured response produced by a provider adapter before the import domain consumes candidate fields, relationships, warnings, confidence categories, and document evidence.
- **Import Warning**: A user-facing notice about missing, ambiguous, conflicting, duplicate, low-confidence, unsafe, unsupported, or incomplete information that may require user attention. It has a review state showing whether the user confirmed, edited, excluded, intentionally left, or has not yet addressed the warning.
- **Work Experience**: A structured employment history item containing an employer and one or more roles. Each role has its own title, location if available, start date, optional end date, ongoing status, responsibilities, achievements, inference status, and review state.
- **Structured Resume**: The confirmed resume data created from reviewed import fields. It becomes the editable source of truth only after explicit user confirmation, remains until deleted by the user, and after source deletion may retain only minimal non-sensitive provenance such as “imported from initial resume” and “confirmed by user”.
- **Manual Structured-Resume Draft**: A blank editable structured-resume draft created at `/resumes/new/manual` without an imported document or import job. Fields entered through this draft are marked as user-added.
- **User Correction**: A change made by the user during review, including editing, removing, adding, excluding, or confirming an extracted field.

## Constitutional Requirements _(mandatory)_

- **Non-technical UX**: The import journey is visual, guided, and written in plain language. Users never see JSON, YAML, prompts, parsing internals, model names, technical diagnostics, provider credentials, session details, or provider configuration; they do receive plain-language disclosure that resume content is sent to the configured AI provider when provider-backed semantic parsing is used.
- **Import-first onboarding**: The feature directly implements the preferred onboarding path by making resume import the prominent option when creating a resume, while preserving manual entry as a fallback.
- **Structured data source of truth**: Imported content enters an unconfirmed import draft first. The structured resume becomes the editable source of truth only after explicit user confirmation. The uploaded document remains a separate source artifact and is never modified.
- **Rendering and ATS readability**: The feature does not generate final documents or change templates. It must preserve resume section relationships such as role, employer, date, location, education, links, and headings in structured data so later rendering can remain human-readable and ATS-readable.
- **AI behavior and provenance**: AI-assisted semantic parsing is the primary semantic extraction path whenever an AI provider is connected, and it must only produce reviewable candidate fields, relationships, evidence, confidence categories, and warnings. It must not invent facts, silently apply changes, expose prompts, follow document-internal instructions, or create the structured resume without user approval.
- **Protected templates**: Templates and visual customization are out of scope. Import must not modify template source code, template configuration, generated PDFs, raw PDF structures, or rendering components.
- **Security and privacy**: Uploaded resumes contain sensitive personal data. Upload requires authentication, import artifacts are available only to the initiating user, uploads and processing are rate-limited, hostile documents are isolated, active content and document instructions are never executed, source-reconstructing artifacts are deleted no later than 7 days after original upload, and full resumes, credentials, and unnecessary personal data must not be logged.
- **Provider independence and no-AI fallback**: Semantic parsing must be expressed through a provider-independent Nuvitae abstraction and versioned Nuvitae extraction schema. The completed T189-T195 result is a NO-GO only for the tested `codex app-server` 0.146.0 ChatGPT-managed authentication candidate. For the Community MVP, direct Codex OAuth through a dedicated infrastructure-level credential broker and direct Codex ChatGPT transport is the production primary AI path, implemented only as an adapter behind the provider-independent boundary and still gated on the direct-OAuth decision-gate conditions. The import domain must not depend on Codex, OpenAI, ChatGPT, Claude, Ollama, provider-native JSON, provider SDKs, or provider tokens. Unavailable AI must not block upload, validation, retry, deletion, manual entry, or review of limited deterministic partial extraction where available, but Nuvitae must not claim reliable full semantic parsing without an available AI provider.
- **Accessibility and recovery**: Upload controls, progress states, warning labels, review fields, correction controls, retry, cancel, discard, deletion, and confirmation must meet WCAG 2.2 AA expectations, be accessible by label, and be keyboard operable. Failure states must explain what happened and give a recoverable next step.
- **Documentation and failure states**: User-facing help must explain supported files, supported languages, bilingual support, upload limits, rendered page limits, selectable-text requirements, configured AI provider use, unsupported-language handling, import privacy, retention, deletion, partial extraction, unsupported documents, and confirmation. Failure states must cover authentication required, validation failure, unreadable content, partial extraction, no-supported-field extraction, no provider, provider unavailable, provider rate-limited, provider unauthenticated, provider quota exceeded, processing failure, cancellation, retry, timeout, rate limiting, unsupported language, ambiguous mixed documents, and expired import drafts.

## Assumptions

- Supported resume documents for this feature are PDF and DOCX files in French, English, or bilingual French-English, up to 10 MB and 5 rendered pages. Import requires selectable text; scanned, image-only, or non-selectable documents are rejected, while documents containing selectable text mixed with images can be processed from the selectable text.
- The initial Community self-hosted release uses AI-assisted semantic parsing as the primary semantic extraction path when a usable provider is connected. For the Community MVP, direct Codex OAuth is the production primary provider through the provider-independent parser boundary, a dedicated Codex credential broker, OAuth Authorization Code with PKCE, broker-owned encrypted credential persistence and refresh, and direct Codex ChatGPT transport; production adapter implementation remains unverified and gated until the direct-OAuth spike records an explicit go, conditional-go, or no-go decision, and the Community product decision does not by itself authorize or complete it.
- The completed T189-T195 spike remains completed and must not be reopened or reclassified as incomplete; its NO-GO applies only to the tested `codex app-server` 0.146.0 ChatGPT-managed authentication candidate, not to Codex globally, direct OAuth, future Codex versions, or the AI-first architecture.
- Completed foundational product and implementation decisions for development workflow, application architecture, private import storage, physical document extraction, validation and provenance, grounding and no-invention enforcement, review and confirmation, manual entry, deterministic partial fallback, and T189-T195 evidence are preserved and are not reopened by the direct-OAuth compatibility spike.

Before any future T201 live authorization may be considered, a separate task must reconcile the strict output schema, fixture-manifest schema and manifests, prompt construction, matrix evaluator, golden-result builder, tests, and T201 status references with FR-009d through FR-009i and FR-021n.
